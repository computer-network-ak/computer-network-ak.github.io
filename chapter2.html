2.3 HTTP, web state and caching

HTTP is a stateless request–response protocol: a client sends a method, target, headers and optional body; a server returns a status code, headers and optional representation. Statelessness makes servers easier to scale because each request contains the information needed to process it.

2.4 QUIC builds secure, reliable streams over UDP

QUIC places transport functions in user space on top of UDP. The UDP header only carries source port, destination port, length, and checksum; QUIC adds connection establishment, TLS 1.3 security, packet numbers, acknowledgments, loss recovery, flow control, congestion control, and multiple streams.

PACKETS CONTAIN FRAMES

A QUIC packet has a packet number and carries one or more frames. Frames describe work such as stream data, acknowledgments, flow-control updates, path validation, or connection close. If a packet is lost, QUIC sends the still-needed frames again in a new packet with a new packet number.

How the connection is established

The client’s first QUIC Initial packet can already carry a TLS ClientHello and transport parameters. The server replies with its TLS key share, certificate, signature, and transport parameters. After both sides verify the handshake transcript, they derive one-round-trip traffic keys. HTTP/3 can then create independent bidirectional or unidirectional streams inside the same encrypted connection.

Loss recovery and acknowledgments

Receivers acknowledge ranges of packet numbers, so one ACK can report both received packets and gaps. Loss is inferred from packet reordering thresholds or time. QUIC retransmits the information carried by lost frames rather than resending an identical packet. ACK-only packets do not elicit an immediate acknowledgment, preventing ACK loops. They can still be acknowledged when later traffic triggers an ACK. ACKs identify packets, not individual frames.

0-RTT

Resume quickly

A returning client can use a resumption secret and remembered server parameters to send replay-safe application data in 0-RTT. Because an attacker can replay early data, applications must not use it for unsafe one-time actions.

CONNECTION ID

Survive address change

Connection IDs identify the connection independently of the IP/port four-tuple. A peer validates a new path and limits traffic until reachability is confirmed.

ANTI-AMPLIFICATION

Protect an unverified address

Before validating a client address, a server limits how many bytes it sends so a spoofed source cannot trigger a large reflected response.

HEAD-OF-LINE ACCURACY

QUIC removes cross-stream transport head-of-line blocking: loss in the HTML stream does not stop complete CSS data from being delivered. Ordered bytes after a gap in the same stream still wait for repair.

Caching, TTL, and failure

Every returned record has a TTL that limits how long a resolver may reuse it. Caching reduces lookup latency and hierarchy load, but an old answer may remain visible until its TTL expires. Resolvers also cache negative answers. NXDOMAIN means the queried name does not exist; SERVFAIL means the resolver could not complete the lookup, perhaps because upstream service or DNSSEC validation failed.

2.8 Socket programming makes protocol roles concrete

UDP SERVER

Bind and receive

Bind a local port, receive one datagram with the sender address, then send a response to that address. Message boundaries are preserved.

TCP SERVER

Listen and accept

Bind, listen, accept a connection, then read and write a byte stream. Each accepted connection has its own socket.

QUIC APP

Secure streams

Open a QUIC connection over UDP, authenticate during setup, and exchange independent reliable streams.

STREAM BOUNDARIES

TCP preserves byte order, not application message boundaries. Applications must define framing using a length field, delimiter, fixed-size record, or self-describing format.

"""One-client local TCP echo demonstration. Run before tcp_client.py."""
import socket

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
    listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    listener.bind(("127.0.0.1", 5050))
    listener.listen(1)
    listener.settimeout(60)
    print("Listening on 127.0.0.1:5050", flush=True)
    connection, peer = listener.accept()
    with connection:
        connection.settimeout(10)
        # Echo chunks; TCP does not preserve the client's write boundaries.
        while True:
            chunk = connection.recv(4096)
            if not chunk:  # Peer has closed its sending direction.
                break
            connection.sendall(chunk)

"""Send a bounded request; read the echo until server EOF."""
import socket

message = b"Hello, networks!\n"
with socket.create_connection(("127.0.0.1", 5050), timeout=5) as connection:
    connection.sendall(message)
    connection.shutdown(socket.SHUT_WR)  # End request, keep receiving.
    received = bytearray()
    while True:
        chunk = connection.recv(4096)
        if not chunk:
            break
        received.extend(chunk)
    assert bytes(received) == message, "Echo differs from request"
    print(received.decode("utf-8"), end="")

"""Send one datagram; timeout is possible because UDP has no recovery."""
import socket

destination = ("127.0.0.1", 5051)
message = b"Hello, datagrams!\n"
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as client:
    client.settimeout(3)
    client.sendto(message, destination)
    try:
        data, sender = client.recvfrom(4096)
    except socket.timeout:
        print("No reply within 3 seconds; UDP does not retry automatically.")
    else:
        assert sender == destination and data == message, "Unexpected reply"
        print(data.decode("utf-8"), end="")

Concept clinic Applied questions: Applications, DNS and QUIC

This section connects application protocols to sockets and transport behavior. It includes a complete DNS walkthrough and resolves the questions about ports, server sockets, DASH, mail, HTTPS, and QUIC.

08Does the transport layer provide encryption and decryption?

Traditional TCP and UDP do not encrypt application data. Security is normally supplied by TLS above TCP, by QUIC’s integrated TLS handshake over UDP, or by IPsec below transport.

TCP supplies reliability, ordering, flow control, and congestion control. Its checksum detects accidental corruption but does not prevent an attacker from reading or changing traffic. HTTPS usually means HTTP protected by TLS. With HTTP/1.1 and HTTP/2, TLS runs over TCP. HTTP/3 runs over QUIC, and QUIC incorporates TLS 1.3 so encryption is part of connection establishment.

The name “Transport Layer Security” can be confusing: in the five-layer teaching model, TLS is commonly placed between the application and transport layers because it uses TCP and protects application bytes. Link encryption such as WPA protects one local hop; IPsec can protect IP packets; end-to-end TLS protects the application exchange across all intervening networks.

09Can an application automatically switch back and forth between TCP and UDP?

TCP and UDP do not automatically replace one another. Any fallback is explicitly designed by the application protocol.

The two transports expose different semantics. TCP is a reliable ordered byte stream with connection state. UDP preserves datagram boundaries but provides no built-in retransmission, ordering, flow control, or connection handshake. An application cannot simply continue the same transport state in the other protocol.

Some protocols define a deliberate fallback. Classic DNS usually tries UDP and repeats over TCP if the answer is truncated. A product may try QUIC/HTTP/3 over UDP and fall back to HTTPS over TCP if UDP is blocked. The application must start the alternative connection, repeat or resume the request safely, and avoid duplicating side effects.

10How does DASH-style adaptive video streaming work?

The server stores short video segments in several quality levels; the client repeatedly chooses which version of the next segment to download over HTTP.

  1. The player obtains a manifest describing segment locations, codecs, resolutions, bitrates, and timing.
  2. It estimates available throughput from recent downloads and observes how many seconds of video are buffered.
  3. It requests the next segment at a representation likely to arrive before playback consumes the buffer.
  4. A CDN edge usually serves the request. The decision repeats for every segment as conditions change.

High quality consumes more bandwidth; low quality protects against rebuffering. A good adaptation algorithm balances picture quality, startup delay, quality changes, and stall risk. Commercial streaming services use adaptive segmented delivery with service-specific encoders, manifests, players, and control logic; DASH explains the core model without implying that every service uses an identical implementation.

11What are the Internet, the Web, a web page, and HTTP?

The Internet is the global packet network. The World Wide Web is an information system that runs on it. A web page is a representation displayed by a browser. HTTP is the application protocol used to request and transfer web resources.

  • Internet: hosts, routers, links, IP addressing, and interconnected administrative networks. It also carries email, voice, games, DNS, and many services beyond the Web.
  • Web: interlinked resources identified by URLs and accessed through browsers and servers.
  • Web page: usually an HTML document plus referenced CSS, JavaScript, fonts, images, video, and API data. Loading one visible page can require many HTTP requests.
  • HTTP: defines request methods, response status codes, headers, caching, and representation transfer. HTTPS is HTTP protected by TLS or QUIC security.

The Internet is the delivery infrastructure; the Web is one service using it; HTTP defines the conversation; the page is the content the browser constructs from the responses.

12How does QUIC work, where does it fit, and which transport does HTTPS use?

QUIC is a secure transport implemented over UDP. HTTP/3 uses QUIC. HTTPS with HTTP/1.1 or HTTP/2 normally uses TLS over TCP; HTTPS with HTTP/3 uses QUIC over UDP.

A QUIC endpoint sends UDP datagrams containing encrypted QUIC packets. During setup, QUIC combines transport negotiation with a TLS 1.3 handshake. After setup it exposes multiple independent reliable streams, loss recovery, flow control, and congestion control. Loss in one stream does not block delivery of bytes already available in another stream, avoiding TCP-level head-of-line blocking between HTTP requests.

Connection IDs let a connection survive a validated path change, such as switching from Wi-Fi to cellular. Most logic runs in user space, allowing faster protocol evolution than kernel TCP. UDP supplies only the datagram envelope; QUIC itself implements the reliable and controlled transport behavior.

13Does a TCP connection reserve network resources in a packet-switched network?

No. A normal TCP connection creates endpoint state, but it does not reserve router buffers, link bandwidth, or a fixed end-to-end path.

The two hosts allocate socket state, send/receive buffers, sequence numbers, timers, and congestion-control variables. Routers forward the resulting IP packets like other traffic. Queueing and competing traffic can change throughout the connection, and packets may even take different paths.

TCP adapts rather than reserves: acknowledgments and loss or congestion signals regulate the congestion window, while the receiver’s advertised window protects receiver memory. A network can separately offer quality-of-service scheduling, traffic engineering, or reservation systems, but those are not created merely by the TCP three-way handshake.

14What are push and pull protocols? Where does SMTP fit?

A push protocol has the sender initiate transfer toward the receiver. A pull protocol has the receiver request content when it wants it.

SMTP pushes a message from a sending mail server to a receiving mail server. If delivery fails temporarily, the sender queues the message and retries. The recipient later accesses stored mail using IMAP or a webmail interface; this access is receiver-driven and behaves like pull or synchronization.

HTTP is usually pull: a client requests a resource and the server responds. Modern systems may keep a connection open so a server can deliver events, but the initial relationship and permission are still established by the application. “Push” and “pull” describe who initiates data movement, not whether TCP or UDP is used.

15Why does DNS usually use UDP if name resolution must be dependable?

Most DNS exchanges are short request/response transactions, so UDP avoids connection setup. Reliability is supplied by retries, multiple servers, caching, and a defined switch to TCP when needed.

A client places an identifier in the query and accepts only a matching response. If no answer arrives before its timer expires, it can retransmit or try another configured resolver. A recursive resolver likewise retries authoritative servers. When a classic UDP answer is too large, the server can set the truncated flag and the client repeats over TCP. Zone transfers use TCP, and encrypted DNS may use TLS, HTTPS, or QUIC.

DNS therefore does not assume that a single UDP datagram is reliable. It builds a dependable lookup service from timeout and retry behavior, redundant servers, cached results, and transport fallback. TCP is useful but does not guarantee the name exists or that an authoritative server is operational.

16What is the complete DNS resolution process?

DNS is a distributed hierarchical database. A stub resolver asks a recursive resolver, which uses cached data or follows delegations to find an authoritative answer.

  1. Stub to recursive resolver: the device sends the full question, such as the A or AAAA record for a host.
  2. Cache check: a valid cached answer or cached negative answer can end the lookup immediately.
  3. Root referral: on a miss, the resolver asks a root server and receives the appropriate top-level-domain name servers.
  4. TLD referral: the resolver asks a TLD server and receives the child zone’s authoritative name servers, with in-bailiwick glue when required.
  5. Authoritative answer: the authoritative server returns the requested data, an alias to follow, or a proof that the name/type does not exist.
  6. Validation and cache: a validating resolver checks DNSSEC signatures when present, caches records according to TTL, and returns the final answer to the stub.

A/AAAA map names to addresses; NS delegates zones; CNAME creates an alias; MX identifies mail exchangers; SOA describes zone authority; TXT carries text policies and verification data. NXDOMAIN means the name does not exist; SERVFAIL means resolution could not be completed. DNSSEC authenticates data but does not encrypt it. DoT and DoH encrypt the client-to-resolver channel but do not replace authoritative DNS.

17How does a client know the destination port number?

The application protocol, URL, configuration, or service-discovery mechanism tells the client which server port to use.

Well-known defaults make common services predictable: HTTP normally uses TCP port 80, HTTPS uses TCP or UDP port 443 depending on the HTTP version, DNS uses port 53, and SMTP server relay commonly uses port 25. A URL may override the default, as in https://example.test:8443/. Applications may learn non-default endpoints from configuration, DNS SRV records, a directory service, or an earlier negotiation.

The client’s own source port is usually selected automatically from the ephemeral range by the operating system. The destination IP identifies the host; the destination port identifies the intended transport endpoint on that host.

18Does every process create its own TCP or UDP implementation?

A process creates one or more sockets. The operating system normally provides the shared TCP/IP implementation used by all processes.

A socket is an OS-managed communication object and the application programming interface to transport. A browser may own many TCP and QUIC sockets; a server may own one listening socket plus thousands of connected sockets. The kernel maintains protocol state, buffers, timers, and packet processing for conventional TCP and UDP.

User-space transports such as QUIC are often implemented by a library inside the process, but they still use UDP sockets supplied by the operating system. “One process equals one transport instance” is therefore too simple: one process can have many endpoints, and one OS protocol stack serves many processes.

19Does a port number belong to a process or to a socket?

A port is a transport-layer endpoint identifier bound to a socket; the socket is owned or referenced by a process.

A process can bind multiple sockets to different ports, and some systems allow controlled port sharing. UDP delivery commonly uses local address and destination port. A TCP connection is uniquely identified by the four-tuple of source IP, source port, destination IP, and destination port. Therefore thousands of clients can connect to the same server IP and port while each accepted connection remains distinct.

Thinking “the process has port 443” is convenient shorthand. More precisely, a server process owns a listening socket bound to local port 443, and the OS demultiplexes incoming segments to that socket or to its accepted child connections.

20What happens when the destination port is unavailable?

If no application is listening, TCP normally rejects the connection with a reset; UDP may trigger an ICMP Port Unreachable response or simply appear to time out.

For TCP, a host receiving a SYN for a closed port commonly returns RST. The client reports “connection refused,” which differs from a timeout caused by filtering, packet loss, or an unreachable host. A firewall can deliberately drop the packet, so the client receives no immediate explanation.

For UDP, there is no connection handshake. The host may send ICMP Destination Unreachable/Port Unreachable, but firewalls and APIs do not always deliver that error to the application. The sending application must define its own response timer and failure behavior.

21Does a TCP server use the listening socket for data transfer?

The listening socket remains the rendezvous point for new connections. Each successful accept creates a separate connected socket for that client’s data.

The server first creates a socket, binds it to a local address and port, and calls listen. When a handshake completes, accept returns a new socket identified by the client/server four-tuple. The server reads and writes application bytes on this connected socket while the original listening socket continues accepting other clients.

This separation lets one server port support many simultaneous connections. Closing one accepted connection does not close the listener. A client does use its connected socket for both connection state and data because it does not need a separate listening role.

ENGINEERING PERSPECTIVE

What production application protocols must handle

Real systems operate with stale caches, duplicate requests, partial failure, middleboxes, and multiple layers of naming and load distribution.

EVOLUTION

QUIC also solves protocol ossification

Transport evolution is limited when middleboxes assume that TCP must always look and behave like older TCP. A new option can be blocked or rewritten even when both endpoints understand it. QUIC places most transport metadata inside authenticated encryption and uses UDP as a widely supported outer envelope.

This protects protocol fields from accidental interference and lets applications update transport code without waiting for operating-system kernel releases. The tradeoff is more user-space complexity, CPU cost, and the need to make UDP traffic acceptable to network policy.

TECHNICAL DRILL-DOWN

QUIC encrypts most transport headers while exposing only the fields needed for routing and demultiplexing. Different packet-number spaces isolate Initial, Handshake, and 1-RTT recovery. Version negotiation and transport parameters let endpoints agree on behavior without middleboxes parsing every extension.

  • Initial packets use keys derived from the destination connection ID; they provide obfuscation and handshake framing, not server authentication.
  • TLS handshake messages travel in QUIC CRYPTO frames. STREAM frames carry application bytes with stream IDs and offsets.
  • A connection ID decouples connection identity from the address four-tuple, but migration still requires path validation and congestion state appropriate to the new path.
NAMING

DNS names services; routing reaches addresses

A domain name is a relatively stable service identifier. DNS may map it to several changing addresses based on region, health, policy, or CDN selection. Routing then finds a path to the chosen address. The two systems solve different indirection problems.

Because clients cache DNS answers, changing an authoritative record does not instantly move every user. Operators coordinate TTL reduction, deployment readiness, health checks, and rollback. DNS-based steering is intentionally approximate; it cannot see every client’s exact path or instantly revoke all cached answers.

TECHNICAL DRILL-DOWN

The resolver returns resource records, not a route. After address selection, the host performs a routing-table lookup, selects a source address and next hop, resolves the next-hop link address, and emits a frame. Happy Eyeballs-style clients may race IPv6 and IPv4 candidates rather than waiting serially.

  • Authoritative DNS can use weighted, latency-informed, or geographic answers, but commonly sees the recursive resolver’s location rather than the exact client.
  • EDNS Client Subnet can reveal a client prefix for steering, with privacy and cache-fragmentation costs.
  • Health-aware DNS must avoid returning an endpoint before it is ready and should keep rollback capacity until old TTLs expire.
CACHING

A cache changes consistency, not only speed

Caching removes work and latency by reusing an earlier answer, but the reused value may be stale. TTL and HTTP freshness rules create an explicit consistency window. A short lifetime improves responsiveness to change and increases origin load; a long lifetime improves efficiency and prolongs old state.

Correct cache keys matter as much as freshness. If a cache ignores language, authorization, encoding, or another request dimension, it may return the wrong representation or leak private content. Invalidation is difficult because copies exist at browsers, recursive resolvers, proxies, CDN edges, and application stores.

TECHNICAL DRILL-DOWN

DNS TTL is carried with each resource record and counts down in recursive caches. HTTP freshness is computed from response headers such as Cache-Control: max-age, s-maxage, Age, and validators such as ETag.

  • Revalidation: a stale HTTP object can be checked with If-None-Match; a 304 response reuses the body.
  • Variant control: Vary extends the cache key. Missing dimensions can serve the wrong language, encoding, or personalized response.
  • Failure strategy: stale-while-revalidate and stale-if-error can trade freshness for availability while an origin is slow or unavailable.

Purging a CDN does not clear browser caches or independent recursive DNS caches; consistency must be designed across every copy.

RETRIES

Reliable transport does not make a transaction exactly once

A client can send a request, the server can commit it, and the response can disappear before reaching the client. From the client’s perspective, “no response” cannot distinguish “request never arrived” from “operation succeeded but response was lost.” A blind retry may perform the action twice.

Safe systems use idempotent operations, request identifiers, deduplication records, conditional updates, or application-level reconciliation. TCP guarantees byte-stream behavior for one connection; it cannot decide whether charging a card twice is acceptable.

FAILURE RULETimeout means the outcome is unknown, not automatically that the operation failed.
TECHNICAL DRILL-DOWN

Distributed systems cannot generally distinguish a lost request from a lost response using timeout alone. “Exactly once” is usually implemented as at-least-once delivery plus duplicate detection inside a well-defined retention window.

  • The client generates an idempotency key and repeats it on every retry of the same logical operation.
  • The server atomically stores the key with the operation result, then returns the stored result for duplicates.
  • The key’s scope must include caller identity and operation type; its lifetime must exceed the maximum retry interval.
  • Conditional writes using versions or ETags prevent a retry from overwriting newer state.
timeout ⇒ {not sent, in flight, rejected, committed, response lost}; outcome remains uncertain
LOAD DISTRIBUTION

“Nearest server” rarely means geographically nearest

CDNs and anycast services choose an endpoint using routing policy, measured latency, capacity, content availability, cost, and failure state. The lowest geographic distance can have a poor network path, while a farther site may have better peering.

Anycast advertises the same IP prefix from multiple locations and lets routing select a site. DNS steering returns different addresses. Both can shift traffic during failure, but existing connections, cached answers, and routing convergence make movement gradual and sometimes uneven.

TECHNICAL DRILL-DOWN

In IP anycast, multiple sites originate the same prefix. BGP policy selects one advertisement, so “nearest” means preferred by the routing system. Traffic may move when a route is withdrawn, and the return path can be independently selected.

  • DNS steering can account for resolver location, measured performance, capacity, content placement, and maintenance state.
  • Layer-4 or layer-7 load balancers select a backend after traffic reaches a site; consistent hashing limits cache disruption when backends change.
  • Connection-oriented traffic needs stability. A route shift to a site lacking connection state can reset TCP, while QUIC may survive only when server keys and connection-routing state support it.
LIFECYCLE

Timeouts, cancellation, and backpressure are protocol features

An application needs deadlines for connect, request, idle, and total operation time. A single generic timeout cannot express all of these. Cancellation should propagate so abandoned work stops consuming server, database, and network resources.

Backpressure means a slow consumer eventually slows producers instead of allowing unbounded queues. TCP offers byte-level flow control, but an application still needs limits on requests, objects, decompression, parsing, and downstream work. Without these limits, a technically valid peer can exhaust memory or create latency collapse.

TECHNICAL DRILL-DOWN

Production clients commonly separate DNS, connect, TLS/QUIC handshake, first-byte, idle-read, and total-request deadlines. Each timer diagnoses a different failure. Randomized exponential backoff prevents many clients from retrying simultaneously after an outage.

  • Transport backpressure: a full receive buffer reduces rwnd; a blocked sender eventually stops writing.
  • Application backpressure: bounded queues, concurrency limits, streaming parsers, and demand-based APIs prevent work from accumulating above the socket.
  • Cancellation: HTTP/2 RST_STREAM, HTTP/3 RESET_STREAM/STOP_SENDING, or connection close can release work, but database or downstream cancellation must also be propagated.
  • Retry budget: cap retries as a fraction of normal traffic so failure recovery does not become the dominant load.

Essential details Details that matter

Check the short answer, then the scope and exceptions. These distinctions prevent common mistakes in exams, interviews, and troubleshooting.

01Is a port a physical connector or a unique process identifier?

A transport port is a 16-bit logical number, not a cable connector. TCP and UDP have separate port namespaces. Ports 0–1023 are System Ports, 1024–49151 are User Ports, and 49152–65535 are Dynamic/Private Ports; operating systems may choose different ephemeral allocation ranges. A port alone does not globally identify a process: addresses, protocol, connection state, and socket-binding rules also matter.

02How can thousands of clients use the same server port?

For ordinary TCP connections, the source IP, source port, destination IP, and destination port distinguish connections. A listening socket accepts connections on the service port; accepted sockets retain that local port but have different peer tuples. A client normally uses an ephemeral source port. A service on port 443 is not limited to one client or one socket.

Link to this answer
03Does DNS resolve an entire URL, and does one name mean one server?

DNS looks up names and record types, not a URL path such as /courses or a fragment such as #review. One name may return multiple addresses, and many names may share an address. DNS caching and load balancing can change the selected endpoint. After DNS, the application still chooses its protocol, connects, and identifies the requested resource.

Link to this answer
04Are NXDOMAIN, an empty DNS answer, and SERVFAIL the same?

No. NXDOMAIN says the queried domain name does not exist. A NOERROR response with no matching answer can mean the name exists but has no record of the requested type, often called NODATA. SERVFAIL means resolution failed, for example because of an upstream failure or failed DNSSEC validation. Diagnose the returned status and authority information before concluding that a website is down.

Link to this answer
05How can HTTP be stateless when websites remember me?

Stateless protocol semantics do not prohibit application state. Cookies, session identifiers, tokens, and server-side records can associate requests with a user. A cookie may hold an identifier or other data; it need not always point to a server-side session. Persistent TCP connections and HTTP authentication are separate concerns. Browser local storage is also different from cookies automatically attached to matching requests.

Link to this answer
06Which HTTP status codes should I recognize?

200 indicates success; 201 indicates creation; 204 has no response content. A 301 or 308 is a permanent redirect, while 302 or 307 is temporary; 307/308 preserve the method. A 304 answers conditional validation without resending the representation. 400 is a bad request, 401 requires authentication, 403 refuses access, 404 means not found, 429 limits request rate, and 5xx codes indicate server-side failure.

Link to this answer
07Does idempotent mean safe, or that every response is identical?

No. Safe methods are intended to read without requesting a state change. Idempotent methods have the same intended effect when repeated as when performed once. DELETE can be idempotent while changing state; its later response may differ. A timed-out payment request may already have succeeded. Retrying a non-idempotent operation needs an application mechanism such as an idempotency key.

Link to this answer
08How do DHCP, DNS, and ARP differ?

DHCP supplies network configuration, DNS maps names to records, and ARP finds the local link-layer address for an IPv4 next hop. They answer different questions: “What configuration may I use?”, “What records describe this name?”, and “Which local MAC should receive this frame?” IPv6 uses Neighbor Discovery rather than ARP. A DNS failure does not necessarily mean that the host lacks an IP address.

Link to this answer
09Does one send() correspond to one recv()?

No. TCP is a byte stream: a read may contain part of a write or bytes from several writes. Define application framing and handle partial reads. A successful send reports local acceptance, not proof that the peer application processed the request. UDP preserves datagram boundaries, but datagrams can be lost, duplicated, reordered, or truncated by an undersized receive buffer.

Link to this answer
10Are the familiar port numbers mandatory?

They are conventions or protocol defaults, not proof of what is running. HTTP commonly uses TCP 80; HTTPS commonly uses TCP 443 or UDP 443 for HTTP/3; DNS uses UDP and TCP 53; SSH uses TCP 22; SMTP relay uses TCP 25. Configuration, proxies, and tunnels can change the observed port. Port numbers alone do not establish service identity or security.

Advanced analysis Application protocols in production

This section connects HTTP framing, mail envelopes, DNS service roles, CDN placement, and the API boundary between HTTP/3 and QUIC.

HTTP/2 multiplexes frames, not independent transports
STREAMS · FRAMES · FLOW CONTROL

HTTP/2 converts requests and responses into binary frames associated with stream identifiers. Frames from many streams share one persistent TCP connection, allowing concurrency without opening one connection per object. HPACK compresses repeated header fields, and stream-level flow control prevents one receiver buffer from being overwhelmed.

TCP still delivers one ordered byte stream. If one TCP segment is missing, later bytes for every HTTP/2 stream wait at the transport boundary. HTTP/3 retains HTTP semantics but maps them to QUIC streams whose reliable delivery is tracked independently.

Electronic mail has an envelope and a message
SMTP · MIME · IMAP

SMTP commands carry the delivery envelope: the reverse path, one or more recipients, and message data. The visible From: and To: headers are part of the message and can differ from envelope addresses. Mail servers use envelope recipients for routing and delivery status.

MIME describes content types, encodings, and multipart boundaries so a message can contain text and attachments. SMTP pushes mail between servers; IMAP synchronizes stored mailboxes; webmail uses HTTP between browser and mail service. Delivery may be delayed and retried, so message identifiers and duplicate handling matter.

DNS provides aliases, mail routing, and service distribution
CNAME · MX · MULTIPLE ANSWERS

DNS does more than map a hostname to one address. A canonical-name record lets a public alias point toward provider-controlled naming. MX records select mail exchangers with preference values. Multiple A or AAAA records can distribute clients among replicated endpoints, although health, caching, and client address selection make this an approximate load-balancing mechanism.

Delegation separates administrative authority: parent zones publish NS records for child zones. Glue addresses break circular dependency when a delegated name server’s hostname lies inside the delegated zone. Caching follows each record’s TTL and can preserve old placement during a migration.

CDN architecture separates placement, selection, and delivery
EDGE · ORIGIN · CACHE MISS

A CDN first decides where to deploy clusters, then how to place content, and finally how to direct each request. A deep-edge design places many smaller sites inside access networks; a regional-hub design uses fewer, larger sites near major interconnection points.

Request mapping can use DNS, anycast, redirects, or application logic. The selected edge serves a cache hit locally. On a miss it retrieves from an origin or parent cache, may coalesce simultaneous requests, stores the object according to policy, and streams bytes to the client. Selection balances latency, load, failure state, content availability, and cost.

HTTP/3 uses a QUIC API rather than a raw UDP API
CONNECTION ID · STREAM ID · PRIORITY

The application opens a QUIC connection over a UDP socket, but HTTP/3 interacts with QUIC concepts. It creates streams, submits headers and body bytes, and associates work with stream IDs. QUIC handles encryption, packetization, stream offsets, acknowledgments, retransmission of lost frame content, congestion control, and flow control.

Stream priority is advisory scheduling information: critical HTML or blocking resources may be delivered before less important media. Connection-level and per-stream limits prevent a peer from consuming unbounded memory. A UDP datagram is only the outer carrier; the reliable streams belong to QUIC.

Technical reference Application-layer mechanisms

Open the technical reference

Application protocols define what communicating processes say and when they say it. The network transports messages; the application defines their meaning.

PROCESS COMMUNICATION

Architecture, process, socket, address

A network application consists of processes on different hosts. The socket is the application’s interface to transport. A server process is identified by host address and a well-known or registered port; a client usually receives an ephemeral local port. Application architecture may be client–server, peer-to-peer, or hybrid. It is separate from the five-layer network architecture.

  • Protocol syntax: fields and encoding.
  • Semantics: meaning of each field.
  • Timing: who sends, message order, and timeout rules.
TRANSPORT CHOICE

Match service to the workload

Reliable file transfer requires complete ordered delivery. Interactive voice values low delay and can tolerate some loss. Video adapts bitrate to available throughput. TCP supplies a reliable ordered byte stream with flow and congestion control. UDP supplies best-effort datagrams with minimal built-in behavior. QUIC builds secure reliable streams and transport control in user space over UDP.

HTTP TRANSACTION

From URL to reusable response

2 · CONNECTTCP+TLS or QUIC establishes protected transport state.
3 · REQUESTMethod, target, headers, and optional body are sent.
4 · RESPONSEStatus, headers, and representation return.
5 · CACHEFreshness and validators control reuse.

HTTP is stateless at the protocol level. Cookies and authorization headers associate requests with application state. Persistent connections avoid repeated setup. HTTP/2 multiplexes streams over one TCP byte stream; HTTP/3 maps HTTP semantics onto independent QUIC streams. Cache-Control determines freshness, while ETag/If-None-Match and Last-Modified/If-Modified-Since enable validation. Range requests retrieve selected bytes.

ELECTRONIC MAIL

Submission, relay, and access

A user agent submits mail to an outgoing server. SMTP relays it between mail servers using a command/response dialogue over TCP. The destination server stores the message; the recipient reads it through IMAP or a web interface. MIME headers describe content types and attachments. SMTP is a push protocol; HTTP and IMAP are used to retrieve or synchronize stored mail.

DNS

Delegation, records, and cache

A stub asks a recursive resolver for a final answer. On a miss, the resolver follows referrals from root to top-level-domain to authoritative servers. A/AAAA map names to addresses; NS delegates zones; CNAME creates aliases; MX selects mail exchangers; SOA carries zone authority and timers. TTL bounds cache lifetime. NXDOMAIN means the name does not exist; SERVFAIL means resolution could not be completed.

VIDEO AND CDN

Adapt delivery to user and path

Adaptive streaming divides video into short segments encoded at several rates. A manifest lists representations; the player selects each next segment using estimated throughput and buffer level. A CDN stores objects at geographically distributed edge sites. DNS or request routing selects an edge; cache hits avoid the origin, while misses fetch and store content.

SOCKET PROGRAMMING

TCP and UDP control flow

A TCP server creates a socket, binds, listens, accepts, then reads and writes the accepted connection. A TCP client creates a socket and connects. A UDP server binds and receives datagrams; a UDP client sends to a destination address without connection setup. TCP preserves bytes and order, not message boundaries, so applications must define framing.

HTTP MESSAGE ANATOMY

Read requests and responses field by field

An HTTP/1.1 request begins with method, request target, and version, followed by headers, a blank line, and an optional body. A response begins with version, status code, and reason phrase, followed by headers and an optional body. Host selects a virtual host; Content-Type identifies representation format; Content-Length or framing identifies body size; Accept expresses preferred formats; Authorization carries credentials; Location gives a redirect target.

CONNECTION COST

Persistent and multiplexed HTTP

Non-persistent HTTP may spend one RTT establishing TCP and another before response bytes arrive for each object, plus DNS and TLS. Persistent HTTP reuses a connection. HTTP/1.1 pipelining is limited by ordered responses. HTTP/2 divides messages into binary frames and multiplexes streams, compresses headers, and prioritizes work, but all streams still share TCP’s ordered byte stream. HTTP/3 retains HTTP semantics while QUIC isolates transport loss by stream.

COOKIES AND CACHE

State and reuse

A server sets a cookie with attributes such as domain, path, lifetime, Secure, HttpOnly, and SameSite. The browser sends matching cookies later; the value often indexes server-side session state. For caching, freshness lifetime determines whether a stored response is directly reusable. A stale response can be conditionally validated: 304 Not Modified reuses the body. Shared caches must obey authorization and Vary rules.

SMTP DIALOGUE

Envelope, message, and access

SMTP uses commands such as EHLO, MAIL FROM, RCPT TO, DATA, and QUIT with numeric replies. The SMTP envelope controls delivery and can differ from visible From/To headers. Message headers describe sender, recipients, subject, date, identifiers, and MIME structure. MIME boundaries combine text and attachments. IMAP keeps server-side folders and synchronization state; webmail accesses the mailbox through HTTP.

DNS MESSAGE DETAILS

Header flags and resource records

A DNS header contains an identifier, QR, opcode, AA, TC, RD, RA, authenticated-data/checking flags, response code, and section counts. Each resource record contains name, type, class, TTL, data length, and type-specific data. UDP is common for ordinary queries; TCP handles zone transfer and responses that need reliable or larger exchange. EDNS extends UDP capacity. DNSSEC adds signed records and denial proofs; DoT/DoH encrypt only the stub-to-recursive channel.

2.9 Concept check

HTTP/1.1 versus HTTP/2?

HTTP/1.1 reuses TCP connections; HTTP/2 also multiplexes framed streams on one connection. Both still inherit TCP’s ordered-byte-stream blocking.

Why can HTTP/3 avoid cross-stream blocking?

QUIC tracks reliable delivery independently for each stream, so a gap in one stream does not stop delivery from another.

Recursive versus iterative DNS?

A recursive server returns the final answer. In an iterative lookup, each contacted server returns the best referral it knows.

Why does caching help DNS and HTTP?

It serves repeated content closer to the requester, reducing latency and traffic toward authoritative or origin servers.
