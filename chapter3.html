LEARNING FRAMEWORKObjectives, sequence, and key distinction
LEARNING OBJECTIVE

How can endpoints add reliable, ordered process delivery above best-effort IP?

CONCEPT SEQUENCE

Demultiplex by ports → number data → acknowledge arrivals → detect loss with timers/ACK patterns → regulate sender with windows.

KEY DISTINCTION

Flow control protects the receiver. Congestion control protects the network. Reliability alone does not make an operation exactly once.

3.1 From host delivery to process delivery

Definition. The transport layer provides communication between application endpoints on hosts. Multiplexing combines traffic from multiple sockets for transmission; demultiplexing delivers incoming traffic to the appropriate socket.

How it works. Transport headers carry ports and protocol-specific state. IP gets data to a host interface; transport processing selects the application endpoint and applies the service its protocol defines.

Example. A computer can browse the web while using DNS because the operating system distinguishes traffic by protocol, addresses, ports, and connection state.

Transport protocols run in end systems. They extend IP’s best-effort host delivery with services such as multiplexing, reliability, ordering and controls.

01

Multiplex

Gather data from multiple application sockets, add transport headers and pass segments downward.

02

Demultiplex

Use header fields to deliver each arriving segment to the correct receiving socket.

03

Identify

UDP commonly uses destination IP and port. TCP identifies a connection with the source and destination IP/port four-tuple.

LIMIT

Transport can add reliability above an unreliable network, but it cannot guarantee bandwidth or delay that the underlying path does not provide.

3.2 UDP is minimal transport

Definition. UDP, the User Datagram Protocol, is a connectionless transport that sends separate messages called datagrams. It preserves message boundaries but does not itself guarantee arrival, ordering, or duplicate suppression.

How it works. An endpoint adds ports, a length, and a checksum to the message. Delivery uses IP; the application must handle missing messages or add recovery when needed.

Example. A small DNS request can fit in one UDP datagram. If no answer arrives, the resolver may retry; UDP itself does not perform that retry.

Why choose UDP?

  • No connection setup delay or per-connection state.
  • 8-byte header versus a typical 20-byte TCP header.
  • The application controls timing, reliability and ordering.
  • DNS commonly uses it; QUIC builds transport features above it.
CHECKSUM

Add 16-bit words with end-around carry and take the one’s complement. The checksum covers a pseudo-header, UDP header, and payload. It detects corruption but does not repair it; it is optional for IPv4 UDP and required for ordinary IPv6 UDP operation.

3.3 Interactive reliability lab

Definition. Reliable data transfer uses error detection and recovery to deliver data according to an agreed service. Automatic Repeat reQuest (ARQ) recovers from detected loss or damage using feedback and retransmission.

How it works. Stop-and-Wait permits one outstanding unit. Go-Back-N pipelines units and retransmits a range after loss in the textbook model; Selective Repeat selectively retransmits and buffers out-of-order units. Sequence numbers distinguish new data from duplicates.

Example. If a receiver gets data but its ACK is lost, a sender may retransmit. The receiver needs sequence state to acknowledge again without delivering the same data twice.

Choose an algorithm and a channel event, then autoplay or advance one network event at a time. Compare normal delivery with data loss, acknowledgment loss, corruption, reordering, duplicate reception, and receiver-window recovery.

3.4 TCP is a reliable controlled byte stream

Definition. TCP, the Transmission Control Protocol, provides a connection-oriented, reliable, ordered byte stream between endpoints. It does not preserve application message boundaries or guarantee a delivery deadline.

How it works. TCP numbers bytes, acknowledges receipt, detects loss, retransmits, and controls the amount in flight using receiver and congestion limits. An application still needs its own message framing and success semantics.

Example. A 5000-byte application write may span several TCP segments. The receiver can obtain those bytes through multiple reads even when no data is lost.

3.5 TCP creates and closes shared state

Definition. A TCP handshake establishes endpoint connection state, including initial sequence numbers and supported options. Connection termination closes the two directions of the byte stream.

How it works. The usual opening exchange is SYN, SYN-ACK, ACK. FIN signals that one sender has no more bytes; RST aborts a connection. This state is maintained by endpoints, not reserved bandwidth in every router.

Example. One endpoint can finish sending a request with an orderly half-close while continuing to receive the reply in the other direction.

3.6 Congestion control protects the path

Definition. Congestion occurs when traffic demand exceeds available network service, causing queues and potentially loss. Congestion control adapts sending behavior to the network; flow control protects the receiver.

How it works. A sender uses a congestion window and possibly pacing to bound traffic in flight. Feedback such as loss, acknowledgments, or explicit marks affects its rate; the receiver advertises a separate receive window.

Example. A receiver may have plenty of free memory while a shared router link is overloaded. Increasing the receive window does not solve that network bottleneck.

CAUSE

Load approaches capacity

Queues build when aggregate arrival rate approaches or exceeds service rate.

COST

Work is wasted

Dropped packets consumed upstream resources, and unnecessary retransmissions add more load.

CONTROL

Endpoints adapt

Senders infer congestion from loss or delay, or routers provide explicit feedback.

TCP limits data in flight with the congestion window cwnd. The usable send window is approximately min(cwnd, rwnd). Slow start increases the window rapidly to discover capacity. Congestion avoidance grows more cautiously. Duplicate acknowledgments may trigger fast retransmit, while a timeout causes a stronger reduction because it suggests more severe congestion.

3.7 Modern transports use richer signals and faster evolution

Definition. ECN is explicit network congestion signaling. BBR is a family of congestion-control algorithms that model delivery rate and propagation time. QUIC is an extensible transport over UDP; these names describe different kinds of mechanisms.

How it works. ECN-capable equipment can mark traffic to signal congestion. Model-based senders estimate path conditions. QUIC moves transport evolution into endpoints while retaining congestion-control responsibilities.

Example. A congestion mark can prompt a sender to reduce pressure before a queue overflows. It is a network signal, not evidence that an application has consumed its data.

ECN

Mark before dropping

A capable router marks congestion in the IP header. The receiver echoes the signal so the sender can reduce its rate without waiting for loss.

BBR

Model the path

Estimates bottleneck bandwidth and minimum round-trip time, then paces traffic near that operating point instead of treating every loss as congestion.

QUIC

Transport in user space

Combines reliable streams, congestion control, TLS security, and connection migration over UDP, allowing deployment without operating-system TCP changes.

Congestion-control fairness depends on competing algorithms, round-trip times, application behavior, and bottleneck scheduling. Equal rate is only one notion of fairness; operators also care about isolation, latency, policy, and efficient utilization.

CONNECTION MIGRATION

TCP identifies a connection by its IP/port four-tuple, so an address change breaks that identity. QUIC uses a connection ID, allowing a validated path change such as moving from Wi-Fi to cellular data.

Concept clinic Applied questions: Reliability and transport control

These answers explain how a best-effort packet network supports reliable transport, why real-time applications make different choices, and how checksums, sequence numbers, windows, flow control, and congestion control fit together.

22How can TCP provide reliable service over unreliable packet switching?

TCP does not make IP packets inherently reliable. It detects missing, damaged, duplicate, and out-of-order data, then repairs the byte stream with endpoint state and retransmission.

  • A checksum detects many accidental bit errors.
  • Sequence numbers identify each byte’s position.
  • Cumulative acknowledgments report the next byte expected.
  • Timers and duplicate acknowledgments trigger retransmission.
  • The receiver discards duplicates and buffers/reorders acceptable data.
  • Flow control protects the receiver; congestion control limits load on the path.

The guarantee has a boundary: if failures persist, TCP eventually reports that the connection failed. It cannot guarantee a bounded delivery time, preserve a connection through every outage, or recover data that the application never handed to it. “Reliable” means that while the connection succeeds, the application receives an in-order, duplicate-free byte stream or an error rather than silently receiving a hole.

23Why do video calls and other real-time applications often prefer UDP?

Real-time media values timely delivery more than perfect delivery. UDP lets the application decide which losses are worth repairing and prevents transport-level ordered delivery from holding newer media behind an old missing packet.

A voice packet arriving after its playback deadline is usually useless. TCP retransmits missing bytes and presents everything in order, so one loss can stall later bytes even when the application would rather play the newest audio. TCP congestion control also changes sending rate according to network conditions; a fixed-rate media encoder that ignores this creates queues, while one forced through a byte stream can experience delay spikes.

UDP itself is not a complete solution. Real-time protocols add timestamps, sequence numbers, jitter buffers, loss concealment, selective retransmission, forward error correction, authentication, and congestion control. Applications must reduce bitrate when the path is congested. QUIC datagrams and WebRTC/RTP systems are examples of transports or frameworks that preserve application control while still behaving responsibly.

24How does a checksum work, and why do several layers check errors?

A checksum summarizes protected bits. The receiver recomputes the value; a mismatch indicates corruption. Different layers check different scopes, so the protection is complementary.

The Internet checksum treats data as fixed-size words, adds them using one’s-complement arithmetic, and transmits the complemented sum. TCP and UDP include a pseudo-header with important IP information as well as the transport header and payload. A matching checksum means “no error was detected,” not mathematical proof that every bit is correct; some error patterns can collide.

A link-layer CRC protects one frame on one hop. At the next router, that frame ends and a new frame is created for the next link. End-to-end transport checking covers data across the whole path, including routers, memory, interfaces, and links with different protections. Application hashes or authenticated tags can protect a complete object and detect malicious modification. Error detection notices a problem; correction may use redundancy, retransmission, or both.

25Are Stop-and-Wait, Go-Back-N, and Selective Repeat flow-control mechanisms?

They are primarily reliable-data-transfer or ARQ protocols. Their windows also limit data in flight, but flow control specifically prevents a sender from overflowing a receiver.

Stop-and-Wait allows one unacknowledged packet. Go-Back-N pipelines up to N packets, uses cumulative acknowledgment, and retransmits from the oldest missing packet. Selective Repeat acknowledges and buffers packets individually and retransmits only missing packets.

A reliability window answers, “Which packets may be sent or need repair?” A flow-control window answers, “How much buffer space can the receiver currently accept?” In TCP, the advertised receive window rwnd supplies flow control, while sequence numbers, acknowledgments, timers, and retransmission supply reliability. One sliding-window design can implement both concerns, but their reasons and signals remain distinct.

26What does TCP’s 32-bit sequence number represent?

A TCP sequence number identifies a byte position in one direction of the byte stream, modulo 232.

If a segment has sequence number 1000 and carries 500 bytes, those bytes occupy positions 1000 through 1499; an acknowledgment of 1500 says that every byte through 1499 has arrived in order and byte 1500 is expected next. Segments can contain many bytes, so the number does not normally count segments.

Each direction chooses its own initial sequence number during the handshake. Sequence arithmetic wraps after 232 positions and is interpreted within a valid window so old and new bytes are not confused. SYN and FIN each consume one position in sequence space even though they do not carry an ordinary application byte.

SEQ=4200, LEN=800 → next expected ACK=5000, assuming all previous bytes arrived.

27Why are flow control and congestion control separate? Can one replace the other?

Flow control protects the receiving host; congestion control protects the network path. Neither signal reveals the other condition, so both are required and they operate together.

A powerful receiver may advertise a large rwnd even while a slow bottleneck router is congested. Conversely, an uncongested high-capacity network may deliver data faster than a small or busy receiving application can consume it. Congestion control limits the congestion window cwnd from ACK, loss, delay, or ECN signals. Flow control limits data according to buffer space advertised by the receiver.

The sender obeys both at once: usable in-flight data is approximately min(rwnd, cwnd), also subject to local implementation limits. They share window machinery but solve different feedback problems, so merging them into one indistinguishable signal would hide whether the receiver or network is the limiting resource.

28Why is a Go-Back-N window limited by the sequence-number space?

Sequence numbers are reused after wraparound. The sender window must leave at least one sequence value outside the active window so a delayed old packet or ACK cannot be mistaken for a new one.

With a k-bit field there are 2k distinct sequence values. In Go-Back-N, the maximum sender window is normally 2k − 1. If all sequence values were simultaneously valid, after wraparound the receiver could not distinguish a retransmission from the next cycle. The receiver window in basic GBN is one because it accepts only the next in-order packet.

Selective Repeat accepts a range of out-of-order packets, so both old and new windows could overlap after wraparound. Its sender and receiver windows are therefore each limited to at most half the sequence space: 2k−1. The chosen practical window can be smaller because of receiver buffer, bandwidth-delay product, congestion, or implementation limits.

For 3-bit numbers, the space is 0–7. GBN may use at most 7 outstanding packets; SR uses windows of at most 4.

ENGINEERING PERSPECTIVE

Subtle transport behaviors seen in real systems

Transport performance depends on feedback timing, queue behavior, ambiguity after loss, and application semantics—not only on header fields and state diagrams.

FEEDBACK

ACK clocking makes TCP partly self-timed

Packets entering the bottleneck emerge at roughly the bottleneck’s service rate. Their acknowledgments return with similar spacing, releasing the sender to transmit more data. This ACK clock converts the path itself into a pacing signal.

Bursty acknowledgments, ACK compression, delayed ACK policies, reverse-path congestion, and offload can distort that signal. Modern stacks therefore combine window control with explicit pacing so a large permitted window is spread over time rather than emitted as a burst.

TECHNICAL DRILL-DOWN

The sender may transmit while both the congestion and receive windows permit it. Each ACK removes acknowledged bytes from flight, allowing new bytes to enter. With a full pipe, ACK arrival spacing approximates the bottleneck departure spacing.

send allowance = min(cwnd, rwnd) − bytes_in_flight
  • Slow start increases cwnd by acknowledged bytes, producing approximately exponential growth per RTT.
  • Congestion avoidance adds roughly one MSS to cwnd per RTT in classic Reno behavior.
  • Packet pacing schedules transmissions across an RTT to reduce bursts from large ACKs, Generic Segmentation Offload, or application wakeups.
  • ACK compression on the reverse path can bunch acknowledgments and falsely invite a forward burst.
MEASUREMENT

Retransmission creates an RTT ambiguity

If a packet is sent, retransmitted, and then acknowledged, the sender may not know which transmission produced the ACK. Using that sample can corrupt the RTT estimate. Karn’s algorithm avoids timing retransmitted data and uses exponential backoff after timeout.

Timestamp options can disambiguate more samples. The deeper lesson is that feedback only helps when the sender can associate it with the event that caused it; otherwise a control loop learns the wrong model.

TECHNICAL DRILL-DOWN

TCP forms a smoothed RTT estimate and variation estimate from valid samples. The retransmission timeout includes a safety margin and is bounded by implementation limits.

RTTVAR ← (1−β)·RTTVAR + β·|SRTT−R|; then SRTT ← (1−α)·SRTT + α·R; RTO ≈ SRTT + 4·RTTVAR
  • Karn’s rule excludes ambiguous ACK samples after retransmission.
  • Exponential backoff doubles RTO after repeated timeout, reducing pressure during severe failure.
  • TCP timestamps echo a sender timestamp and improve RTT sampling. QUIC avoids retransmission ambiguity by never reusing a packet number; ACK ranges identify exactly which transmission arrived.
QUEUES

More buffering can make a network worse

A large queue prevents packet loss during bursts but can hold seconds of traffic. TCP may interpret the lack of loss as permission to continue, so interactive traffic waits behind bulk transfers. This is bufferbloat: high throughput accompanied by poor latency.

Active queue management such as CoDel or PIE drops or marks packets before a queue remains persistently full. Fair queueing isolates flows so one sender cannot monopolize waiting time. Capacity alone does not solve latency if queue policy allows standing queues.

TECHNICAL DRILL-DOWN

A tail-drop queue signals congestion only after it fills. Multiple flows can then lose packets together, reduce their windows together, and grow together—global synchronization. Active queue management tries to signal before persistent saturation.

  • CoDel: tracks minimum packet sojourn time over an interval and drops when delay remains above a target.
  • PIE: estimates queueing delay and adjusts probabilistic marking or dropping with a control loop.
  • ECN: marks capable packets instead of dropping them; endpoints still reduce sending rate.
  • Fair queueing: separates flows into queues and schedules them, limiting the delay one bulk flow imposes on another.

Measure loaded latency alongside throughput. A speed test that reports only Mb/s can hide seconds of queueing delay.

LOSS INFERENCE

Reordering is not loss

Multipath routing, wireless scheduling, parallel processing, and retransmission can make later packets arrive first. A receiver reports a gap, but the missing packet may still be in flight. Retransmitting too quickly wastes bandwidth; waiting too long delays recovery.

Loss detectors use packet thresholds, time thresholds, selective acknowledgments, and reordering history. QUIC’s explicit packet numbers and ACK ranges improve visibility, while TCP SACK reports received byte blocks. A correct protocol must tolerate both duplication and reordering.

TECHNICAL DRILL-DOWN

Classic TCP inferred loss after three duplicate ACKs, an approximation that can fail under heavy reordering. SACK options describe noncontiguous byte ranges already held by the receiver, allowing the sender to repair only missing ranges.

  • Modern loss detection can combine duplicate/packet thresholds with elapsed time relative to RTT.
  • RACK uses transmission time and acknowledgment of later packets to infer that an older packet is lost.
  • QUIC ACK frames encode packet-number ranges. A lost packet number is never reused; retransmitted STREAM data appears in a new packet.
  • Receiver reassembly buffers consume memory, so protocols enforce windows and may discard data outside the acceptable range.
FAIRNESS

Congestion-control fairness is a policy outcome

Two flows do not necessarily receive equal throughput. RTT, congestion algorithm, start time, number of parallel connections, packet size, application demand, and bottleneck scheduler all matter. A sender with a shorter feedback loop may increase its rate more quickly.

“Fair” can mean equal flow rates, equal users, paid service classes, deadline priority, or protection for latency-sensitive traffic. Congestion control provides a distributed operating rule; queue scheduling and network policy decide how competing goals are balanced.

TECHNICAL DRILL-DOWN

Classic additive-increase/multiplicative-decrease tends toward equal shares among similar long-lived flows at one bottleneck, but the assumptions rarely hold exactly. A connection with a shorter RTT performs more increase cycles per second, and an application opening several connections receives several flow shares.

  • Reno/CUBIC: react primarily to loss; CUBIC grows the window as a function of time since reduction.
  • BBR: estimates bottleneck bandwidth and minimum RTT, then controls pacing and in-flight volume from a model.
  • Scheduler influence: fair queueing, weighted queues, policing, and shaping can dominate endpoint algorithms.
  • Evaluation: compare utilization, queue delay, loss, convergence, RTT bias, and coexistence—not throughput alone.
CAPACITY

The bandwidth-delay product sizes the pipe

The product of bottleneck rate and round-trip time estimates how much data must be in flight to fully utilize a path. A 1 Gb/s path with 100 ms RTT holds about 100 Mb, or 12.5 MB, before counting protocol overhead.

If cwnd, rwnd, or socket buffers are smaller than the path’s bandwidth-delay product, throughput cannot reach the link rate even with zero loss. If queues add delay, the apparent product grows but the extra in-flight data may only sit in a buffer. Good tuning targets the real propagation path and avoids building a standing queue.

PATH MODELThroughput needs enough data in flight; low latency needs that data moving through the path rather than waiting in a queue.
TECHNICAL DRILL-DOWN

BDP uses bottleneck delivery rate and base RTT. Base RTT approximates propagation and processing without persistent queueing; using an inflated RTT includes queued bytes and encourages an oversized window.

BDP = bottleneck_rate × base_RTT; 1 Gb/s × 0.1 s = 100 Mb = 12.5 MB
  • To sustain the target rate, congestion window, receive window, and socket buffers must support roughly one BDP plus implementation margin.
  • TCP window scaling allows advertised windows beyond 65,535 bytes by negotiating a scale during the SYN exchange.
  • Large buffers increase memory use and can amplify queueing. Autotuning grows buffers from observed demand while congestion control limits safe bytes in flight.
  • On lossy long-fat networks, selective recovery and pacing matter because one timeout wastes a large amount of potential transfer time.

01In which layer do we perform flow control?

Both the transport layer and some data-link protocols can provide flow control, with different scopes. TCP limits an end-to-end sender using the receiver’s advertised window; QUIC has stream and connection limits. Ethernet PAUSE is an optional link-level mechanism between neighboring interfaces. Applications can also apply backpressure to their own queues. “Flow control is only at layer 2” and “only at layer 4” are both incomplete answers.

02How is flow control different from congestion control and error control?

Flow control prevents a sender from overwhelming a receiver. Congestion control adapts traffic to network capacity. Error control detects damage and may recover from loss, duplication, or reordering. In TCP, rwnd is a receiver limit and cwnd is a sender’s congestion limit. A clean network can still have a slow receiver, and a fast receiver does not imply that the network has spare capacity.

03How much new TCP data can I send when bytes are already in flight?

In the simplified teaching model, additional allowance is max(0, min(cwnd, rwnd) − bytes in flight). If cwnd is 64 KiB, rwnd is 12 KiB, and 8 KiB is outstanding, the allowance is 4 KiB. Real implementations also track sequence-space window edges, recovery state, pacing, and application availability. The advertised window is not a promise of application processing speed.

04Does a TCP ACK prove that the receiving application processed my data?

No. It reports transport receipt of bytes, not a successful database commit, file save, or payment. An application acknowledgment has a different meaning. After a disconnect, the sender may be unsure whether an operation finished. Exactly-once effects require application design, such as transaction identifiers and duplicate detection; TCP reliability alone cannot supply that guarantee.

05Does TCP number packets, bytes, or messages?

TCP sequence numbers describe byte positions modulo 2³². A segment beginning at sequence 1000 and carrying 500 bytes covers positions 1000–1499; the cumulative ACK is 1500 if all earlier bytes arrived. SYN and FIN each consume one sequence number. An ACK without data, SYN, or FIN consumes no sequence number. Application message boundaries are not encoded by TCP.

06What happens when the receiver advertises a zero window?

The sender stops sending ordinary new data beyond the receive window. Zero-window probing lets it discover that space is available even if a window update was lost. A zero window is receiver backpressure, not automatically packet loss or network congestion. The receiving application must drain buffered data before the advertised capacity can recover.

07How are MTU and TCP MSS different?

MTU is a link’s maximum network-layer packet size; MSS is a TCP payload-size limit. With a 1500-byte IP MTU and no IP or TCP options, the usual calculation is 1460 bytes for IPv4 or 1440 for IPv6. Options and tunnels reduce the effective payload budget. Each endpoint advertises an MSS; the sender must also respect path MTU. MSS does not include the TCP header. See why Ethernet uses 1500 bytes, the 1460-byte calculation, and the complete header breakdown.

08Is UDP always faster, and can it be reliable?

UDP avoids a transport handshake and supplies a small header, but performance depends on the workload and path. An application may implement acknowledgments, recovery, ordering, pacing, and congestion control above UDP, as QUIC does. That does not make UDP itself reliable. Real-time media may prefer late packets to be discarded, whereas a file-transfer protocol must recover missing content.

Link to this answer
09Why can TCP close take four messages, and what is TIME_WAIT?

Each direction of a TCP byte stream closes independently, so FIN and ACK exchanges may use four segments; an ACK and FIN can also be combined. TIME_WAIT retains state long enough to handle delayed duplicates and retransmit the final ACK if needed. It normally occurs at the actively closing side. A reset aborts a connection and has different semantics from an orderly FIN close.

10Why do Go-Back-N and Selective Repeat need different sequence spaces?

With m sequence bits, the textbook Go-Back-N sender window is at most 2^m − 1. With equal Selective Repeat windows, each is at most 2^(m−1). Selective Repeat accepts out-of-order packets and needs separation between old and new windows. These bounds assume bounded packet lifetime; they do not solve arbitrary delay across repeated sequence-number reuse. State whether an ACK names the last accepted or next expected packet.

Sizes, headers & limits Transport layer: header fields, windows, and checksums

Understand the reason behind each number. Header sizes belong to specific protocols; worked examples state the assumptions needed to use them.

Why UDP has an 8-byte header

Source port, destination port, length, and checksum each occupy 16 bits: 4 × 2 = 8 bytes. Length includes the UDP header and data. The ordinary 16-bit field can encode at most 65,535 bytes, but IPv4’s total-length limit leaves at most 65,507 UDP payload bytes with a 20-byte IP header. That theoretical size usually requires fragmentation; at MTU 1500, the corresponding unfragmented payload limit is 1472.

Why TCP headers range from 20 to 60 bytes

The fixed fields occupy 20 bytes. The four-bit Data Offset counts 32-bit words, so its maximum value 15 describes 60 header bytes; options and padding have at most 40 bytes. Options carry capabilities such as MSS, window scaling, timestamps, and SACK. The 1460-byte result assumes minimum headers; follow the MTU/header lesson in Chapter 4 for the complete byte budget.

Why TCP window scaling exists

The base receive-window field is 16 bits: at most 65,535 bytes. That can be too small on a high-rate, long-RTT path. The Window Scale option negotiates a shift during connection setup; the window in SYN-bearing segments is not scaled. The receive window controls receiver capacity, whereas the sender’s congestion window controls network pressure. Neither is a segment-size limit.

Why a pseudo-header is not extra transmitted overhead

TCP and UDP checksums include selected IP information, the transport header, and data. The pseudo-header is constructed for checksum computation; it is not appended as another header on the wire. IPv4 UDP can omit its checksum using a zero field, while ordinary IPv6 UDP requires it. TCP requires a checksum. These checks detect accidental corruption, not a malicious sender.

A window can limit a fast connection

Ignoring loss and overhead, a 65,535-byte window over a 100 ms RTT gives 65,535 × 8 / 0.1 = 5.24 Mb/s. A 100 Mb/s path needs about 1,250,000 bytes in flight at that RTT. Window scaling helps represent a larger receive window, but it does not override congestion control or create capacity.

Advanced analysis Reliability, control, and implementation tradeoffs

This section develops exact demultiplexing rules, UDP’s narrow service, ARQ protocol evolution, and the separate state machines required for reliable transfer and congestion control.

UDP and TCP demultiplex differently
PORTS · SOCKET IDENTIFIERS

A UDP endpoint is commonly selected by local IP address and destination port. Datagrams from different remote hosts can arrive at the same socket, and recvfrom reports each sender. A connected UDP socket can restrict the accepted peer, but UDP still does not create TCP-style connection state.

A TCP connection is identified by source address, source port, destination address, and destination port. The listening socket receives connection requests; each accepted socket gets a distinct four-tuple. This is why many clients can share one server port and why two connections using the same client port remain distinct when their addresses differ.

The UDP checksum protects an end-to-end scope
PSEUDO-HEADER · ONE’S COMPLEMENT

The checksum covers the UDP header and payload plus a pseudo-header derived from IP source, destination, protocol, and length. The pseudo-header helps detect misdelivery to the wrong network-layer endpoints even though it is not transmitted as part of UDP.

The sender adds 16-bit words with end-around carry and complements the result. The receiver repeats the calculation. A mismatch detects corruption, but UDP does not define retransmission. Link CRCs remain useful for each hop; the transport checksum covers faults across the path, including links without equivalent protection and corruption in device memory.

ARQ protocols evolve by removing one ambiguity at a time
CHECKSUM · ACK · SEQUENCE · TIMER

A reliable protocol over bit errors first needs error detection and receiver feedback. If acknowledgments can be corrupted or lost, retransmission creates duplicates. Sequence numbers let the receiver distinguish new data from a repeated packet. If data or feedback can disappear silently, the sender also needs a timer.

Stop-and-Wait needs only two sequence values because at most one packet is unresolved. Pipelining increases utilization on long-delay paths but requires a window, multiple sequence values, and rules for cumulative or selective acknowledgment. A finite-state machine makes the legal event/state combinations explicit.

A TCP segment carries control state as well as bytes
FLAGS · OPTIONS · WINDOWS

Besides ports, sequence and acknowledgment numbers, TCP carries header length, flags, advertised receive window, checksum, urgent pointer, and negotiated options. SYN exchanges initial sequence numbers and options such as MSS, window scaling, selective acknowledgment capability, and timestamps.

ACK is cumulative, while SACK options describe additional received byte ranges. FIN consumes sequence space and closes one direction; both directions may close independently. RST aborts state immediately. TIME_WAIT protects a later connection from delayed segments and permits retransmission of the final ACK.

Congestion creates costs before packets are dropped
QUEUEING · WASTED WORK · COLLAPSE

As load rises, queueing delay grows before loss. When a packet is dropped after crossing several links, all upstream transmission work was wasted. Premature retransmissions consume still more capacity, and multiple paths can create loops or duplicate work during instability.

End-to-end control infers congestion from loss, delay, delivery rate, or acknowledgments. Network-assisted control uses explicit marks or rates. UDP applications that add reliability must also implement congestion response; otherwise successful delivery for one sender may come at the expense of every competing flow.

Technical reference Transport-layer mechanisms

Open the technical reference

Transport extends host-to-host delivery into logical communication between processes and controls reliability, receiver capacity, and network load.

MULTIPLEXING

Ports connect segments to sockets

The sender multiplexes data from many sockets into transport segments. The receiver demultiplexes each segment to the correct socket. UDP commonly identifies a destination socket using destination IP and port. A TCP connection is identified by source IP, source port, destination IP, and destination port, allowing one server port to support many clients.

UDP

Small header, application responsibility

UDP adds source port, destination port, length, and checksum. It provides no handshake, retransmission, ordering, flow control, or congestion control. The checksum uses one’s-complement addition over a pseudo-header, UDP header, and data; it is optional in IPv4 and required for ordinary IPv6 UDP use. UDP suits DNS, real-time media, and protocols such as QUIC that implement their own control.

Stop-and-wait is simple but underuses long, fast paths. Go-Back-N uses a cumulative ACK and retransmits from the oldest missing packet. Selective Repeat independently acknowledges packets and retransmits only missing ones, requiring receiver buffering and careful sequence-number space sizing.

TCP BYTE STREAM

Sequence bytes, acknowledge next expected byte

TCP sequence numbers identify byte positions. The ACK number is cumulative and names the next byte expected. The header includes ports, sequence and ACK numbers, flags, receive window, checksum, and options. MSS limits TCP payload size; IP MTU limits the IP packet carried by a link, excluding Ethernet framing. TCP estimates RTT and uses a smoothed deviation to choose a timeout that adapts without reacting to every sample.

FLOW CONTROL

Protect the receiver

The receiver advertises available buffer space as rwnd. The sender limits unacknowledged data so a fast sender does not overflow a slow application. A zero window pauses normal data; window probes prevent both sides from waiting forever after space returns.

CONGESTION CONTROL

Protect the path

The congestion window cwnd limits in-flight data according to network conditions. Slow start grows quickly; congestion avoidance grows cautiously. Timeout indicates severe congestion; duplicate ACK or selective acknowledgment can reveal isolated loss. ECN marks congestion before loss. BBR estimates bottleneck bandwidth and propagation RTT rather than treating every loss as the main signal.

CONNECTION MANAGEMENT

Synchronize and close state

The three-way handshake exchanges initial sequence numbers and confirms both directions. SYN, SYN-ACK, ACK avoids confusing delayed duplicates with a new connection. Each direction closes independently with FIN; TIME_WAIT lets delayed segments expire and allows the final ACK to be repeated.

QUIC

Transport evolution above UDP

QUIC integrates TLS 1.3, uses monotonically increasing packet numbers, acknowledges ranges, multiplexes independent streams, and supports connection migration through connection IDs. Lost packets are not recreated; their required frames are placed in new packets. QUIC still performs flow control and congestion control.

UDP CHECKSUM

End-around-carry arithmetic

The sender divides the pseudo-header, UDP header, and payload into 16-bit words, adds them using one’s-complement addition, and complements the result. The receiver includes the transmitted checksum; an all-ones result indicates no detected error. The pseudo-header binds the segment to IP source, destination, protocol, and length. A checksum detects many errors but is not cryptographic integrity.

RDT PROGRESSION

Why each mechanism appears

rdt1.0 assumes a perfect channel. rdt2.x handles bit errors with checksum, ACK/NAK, and sequence numbers to survive corrupted control messages and duplicates. rdt3.0 adds a timer for lost data or ACKs. The sender’s state determines which ACK is meaningful; the receiver repeats the last correct ACK when corruption or duplication occurs.

For Selective Repeat, the sequence-number space must be at least twice the window size so an old packet cannot be mistaken for a new packet after wraparound.

TCP HEADER AND OPTIONS

Interpret a segment

Ports identify applications. Sequence and acknowledgment numbers track bytes. Data offset locates payload. SYN, ACK, FIN, RST, PSH, and other flags signal control. The advertised window supports flow control. The checksum covers a pseudo-header, TCP header, and data. Options negotiate MSS, window scaling, timestamps, and selective acknowledgment capability.

TCP LOSS RECOVERY

Timer and acknowledgment evidence

A timeout retransmits the oldest unacknowledged data and backs off the timer. Repeated ACKs indicate that later bytes arrived beyond a gap; fast retransmit repairs the likely missing segment before timeout. SACK identifies received byte ranges so the sender can repair multiple losses efficiently. Karn-style logic avoids measuring RTT from ambiguous retransmissions.

CONGESTION: CAUSES AND COSTS

Offered load is not useful throughput

As input approaches link capacity, queueing rises. When buffers overflow, packets are discarded; upstream transmission capacity spent on a packet that is later dropped is wasted. Premature timeout can create unnecessary duplicates, further increasing load. In multi-hop paths, congestion near the destination wastes all capacity previously consumed by dropped packets. The goal is high goodput with controlled delay and fair sharing, not simply maximum sending rate.

CLASSIC TCP CONTROL

ACK clock and window adjustment

Effective sending window is limited by min(cwnd, rwnd). Slow start increases cwnd roughly by one MSS per ACK, approximately doubling each RTT. Congestion avoidance increases about one MSS per RTT. Timeout resets more aggressively; fast recovery after duplicate ACK evidence preserves more progress. Exact behavior differs among Reno, CUBIC, and implementations.

RECENT CONTROL AND FAIRNESS

Different signals, same shared path

CUBIC grows the window as a cubic function of time around the previous maximum. Delay-sensitive algorithms react before loss. BBR models bottleneck bandwidth and minimum RTT to choose pacing and in-flight volume. ECN-capable routers mark rather than drop; endpoints reduce load after receiving the signal. Fairness depends on RTT, algorithm, number of flows, application limits, and bottleneck scheduling.

TRANSPORT EVOLUTION

Where new functions can live

Transport behavior in operating-system TCP evolves slowly because middleboxes may assume familiar headers. QUIC encrypts most transport metadata and runs in user space over UDP, enabling faster deployment. Applications can open many streams without many kernel TCP connections, but still require responsible congestion control and path validation.

KEEP THE THREE CONTROLS SEPARATE

Reliability repairs missing or corrupted information. Flow control protects the receiving host. Congestion control protects the network path.

3.8 Concept check

Why are sequence numbers needed in Stop-and-Wait?

If an ACK is lost, the sender retransmits. The sequence number lets the receiver detect and discard a duplicate.

Go-Back-N versus Selective Repeat?

GBN accepts only in-order packets and retransmits from the missing base. SR buffers out-of-order packets and retransmits only missing packets.

Multiplexing versus demultiplexing?

Multiplexing combines data from source sockets. Demultiplexing uses header fields to deliver an arrival to the right destination socket.

Why can transport add reliability but not bandwidth?

Endpoints can implement checksums, ACKs and retransmissions. Link capacity and queueing resources lie inside the network.

What exactly does a TCP ACK mean?

It is the sequence number of the next byte expected, so it cumulatively acknowledges all earlier bytes.

Why three handshake steps?

Both endpoints must confirm two-way reachability and synchronize their own initial sequence numbers.
